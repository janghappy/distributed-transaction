# 분산 트랜잭션 패턴 정리 — TCC, SAGA

> [README](../README.md)로 돌아가기

## 1. TCC 패턴

TCC는 여러 서비스의 작업을 **Try → Confirm → Cancel**의 3단계로 처리하는 분산 트랜잭션 패턴입니다.

| 단계 | 의미 |
|---|---|
| **Try** | 예약 및 준비 — 재고 확보, 포인트 사용 가능 여부 확인 |
| **Confirm** | 모든 작업 성공 시 확정 |
| **Cancel** | 실패 시 예약 취소 |

예를 들어 주문 서비스에서 재고와 포인트를 처리한다면 다음과 같습니다.

1. **Try**: 재고 1개를 예약하고 포인트 사용 가능 금액을 확보합니다.
2. **Confirm**: 모든 준비가 성공하면 재고 차감과 포인트 사용을 확정합니다.
3. **Cancel**: 준비 과정에서 실패하면 재고 예약과 포인트 확보를 해제합니다.

```
            ┌─ Try(product: 재고 예약) ─┐   모두 성공   ┌─ Confirm(product) ─┐
order ──────┤                          ├─────────────▶┤                    ├──▶ 주문 확정
            └─ Try(point: 포인트 확보) ─┘               └─ Confirm(point) ───┘
                        │ 하나라도 실패
                        └──────────────▶ Cancel(product), Cancel(point) ──▶ 주문 취소
```

- **장점**: 실제 확정 전에 각 서비스가 필요한 자원을 확보하므로 비즈니스 수준의 일관성을 강하게 제어할 수 있습니다.
- **단점**: 모든 참여 서비스에 Try, Confirm, Cancel 로직을 구현해야 하며, 예약 자원의 만료 및 동시성 제어도 필요합니다.

## 2. SAGA 패턴

SAGA는 여러 서비스의 **로컬 트랜잭션을 순차적으로 실행**하고, 중간에 실패하면 이미 완료한 작업을 **보상 트랜잭션**으로 되돌리는 패턴입니다.

```
1. 주문 생성      ✅ (주문 서비스 커밋)
2. 결제 승인      ✅ (결제 서비스 커밋)
3. 재고 확보      ❌ 실패
        │
        └─▶ 보상 트랜잭션 실행: 결제 취소 → 주문 취소
```

SAGA에서는 각 서비스의 DB 트랜잭션이 독립적으로 커밋됩니다. 따라서 전체 작업을 하나의 DB 트랜잭션으로 묶지 않습니다.

- **장점**: 서비스 간 결합도가 낮고, Kafka 같은 메시지 브로커를 활용해 비동기 처리하기 좋습니다.
- **단점**: 보상 로직을 별도로 구현해야 하며, 처리 도중에는 일시적으로 데이터가 불일치할 수 있습니다.

### SAGA 구현 방식: Choreography vs Orchestration

SAGA는 **각 단계를 누가 이어 주느냐**에 따라 두 가지 방식으로 구현합니다.

#### Choreography (코레오그래피, 이벤트 기반)

중앙 조정자 없이, **각 서비스가 이벤트를 발행하고 다른 서비스가 그 이벤트를 구독**해 다음 작업을 이어 갑니다.

```
Order Service ──(OrderCreated)──▶ Payment Service ──(PaymentApproved)──▶ Inventory Service
      ▲                                  ▲                                        │
      │                                  │                                (StockReserveFailed)
      └──────(PaymentCancelled)──────────┴──── 결제 취소 ◀─────────────────────────┘
   주문 취소
```

1. Order Service가 주문을 저장하고 `OrderCreated` 이벤트를 발행합니다.
2. Payment Service가 이를 구독해 결제를 승인하고 `PaymentApproved`를 발행합니다.
3. Inventory Service가 재고 확보에 실패하면 `StockReserveFailed`를 발행합니다.
4. Payment Service가 이를 구독해 결제를 취소하고 `PaymentCancelled`를 발행하면, Order Service가 주문을 취소합니다.

- **장점**: 중앙 조정자가 없어 서비스 간 결합도가 낮고, 새 서비스를 이벤트 구독만으로 붙이기 쉽습니다. 단일 장애 지점이 없습니다.
- **단점**: 전체 흐름이 여러 서비스의 이벤트 처리에 흩어져 있어 한눈에 파악하기 어렵고, 디버깅·추적이 어렵습니다.

#### Orchestration (오케스트레이션, 중앙 조정)

**오케스트레이터(조정자)가 전체 흐름을 알고**, 각 서비스에 순서대로 명령을 보내고 결과에 따라 다음 단계나 보상 트랜잭션을 지시합니다.

```
                    ┌──▶ Payment Service   : 결제 승인  ── 성공
Order Orchestrator ─┼──▶ Inventory Service : 재고 확보  ── 실패
                    │
                    └──▶ (보상) Payment Service : 결제 취소 → 주문 취소
```

- **장점**: 흐름이 한곳에 모여 있어 이해·변경·모니터링이 쉽고, 보상 순서를 명확하게 제어할 수 있습니다.
- **단점**: 오케스트레이터에 로직이 집중되어 결합도가 높아지고, 오케스트레이터가 장애 지점이 될 수 있습니다. 흐름 상태를 저장·복구하는 설계가 필요합니다.

| 구분 | Choreography | Orchestration |
|---|---|---|
| 흐름 제어 | 각 서비스가 이벤트에 반응 (분산) | 오케스트레이터가 지시 (중앙) |
| 통신 | 주로 이벤트 발행·구독 (Kafka 등) | 명령·응답 (API 호출 또는 명령 메시지) |
| 결합도 | 낮음 | 오케스트레이터에 집중 |
| 흐름 파악·디버깅 | 어려움 (이벤트를 따라가야 함) | 쉬움 (오케스트레이터 코드에 흐름이 있음) |
| 보상 처리 | 각 서비스가 실패 이벤트를 구독해 처리 | 오케스트레이터가 보상 순서를 지시 |
| 적합한 경우 | 참여 서비스가 적고 흐름이 단순할 때 | 참여 서비스가 많거나 흐름·보상 규칙이 복잡할 때 |

## 3. TCC와 SAGA 비교

| 구분 | TCC | SAGA |
|---|---|---|
| 핵심 방식 | 사전 예약 후 확정 또는 취소 | 작업 실행 후 실패 시 보상 |
| 주요 단계 | Try / Confirm / Cancel | 로컬 트랜잭션 / 보상 트랜잭션 |
| 자원 확보 | 일반적으로 사전 확보 | 실행 시점에 확보 |
| 구현 복잡도 | Try·Confirm·Cancel 구현 필요 | 보상 트랜잭션 설계 필요 |
| 적합한 사례 | 재고 예약, 포인트 확보, 좌석 예약 | 주문·결제·배송 등 여러 서비스의 업무 흐름 |

## 4. 실무에서의 선택

실무에서는 일반적으로 **SAGA 패턴을 더 범용적으로 적용**하고, **강한 사전 예약과 확정 절차가 필요한 경우 TCC를 고려**합니다.
다만 서비스 도메인과 일관성 요구사항에 따라 달라집니다.

| 상황 | 일반적인 선택 | 이유 |
|---|---|---|
| 주문 → 결제 → 배송 | SAGA | 서비스별 트랜잭션과 보상 처리로 업무 흐름 구성 |
| 재고 예약 → 주문 확정 | TCC 또는 예약 기반 SAGA | 재고 중복 확보 방지와 예약 만료 관리가 중요 |
| 좌석·항공권 예약 | TCC 또는 예약/만료 방식 | 한정된 자원을 먼저 확보해야 함 |
| 포인트 사용·쿠폰 발급 | 요구사항에 따라 선택 | 중복 사용 방지와 취소 정책이 중요 |
| 단일 DB 내 여러 테이블 갱신 | 일반 DB 트랜잭션 | 분산 트랜잭션 패턴이 불필요 |

### 왜 SAGA를 더 범용적으로 사용할까?

SAGA는 각 서비스가 기존의 로컬 트랜잭션을 유지하면서 실패 시 보상 로직을 추가하는 방식이기 때문입니다.

```
Order Service      주문 생성 및 DB 커밋
      │
      ▼  Kafka 이벤트 발행 (OrderCreated)
Payment Service    결제 승인
      │
      ▼
Inventory Service  재고 확보
      │
      └─ 실패 시 ─▶ 결제 취소 및 주문 취소 이벤트 처리
```

이 구조에서는 각 서비스가 자신의 DB 트랜잭션을 관리하므로 서비스 간 DB 락을 공유할 필요가 없습니다.
대신 **이벤트 중복 처리, 메시지 유실 방지, 보상 작업의 재시도** 등을 설계해야 합니다.

### TCC는 언제 사용하는가?

TCC는 단순히 실패한 작업을 되돌리는 것보다 **작업을 확정하기 전에 자원을 먼저 확보하는 것이 중요한 경우**에 적합합니다.

1. **Try**: 재고 1개를 예약하고 다른 주문이 가져가지 못하도록 합니다.
2. **Confirm**: 결제가 준비되면 예약을 확정합니다.
3. **Cancel**: 결제에 실패하면 예약을 해제합니다.

단, TCC라고 해서 자동으로 동시성 문제가 해결되는 것은 아닙니다.
Try 단계에서 DB 조건부 UPDATE, 락 또는 원자적 연산 등을 통해 재고 초과 예약을 방지해야 합니다.

### 함께 쓰기

SAGA와 TCC 중 하나만 선택해야 하는 것은 아닙니다.
전체 주문 프로세스는 SAGA로 관리하면서, 재고 확보 단계에는 TCC와 유사한 예약·확정 방식을 적용할 수도 있습니다.
